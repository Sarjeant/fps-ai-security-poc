Securing AI agents on instant-payment rails

What happens when an AI assistant that pays invoices reads a fraudster's instructions hidden in the payment message? And can fraudsters change their behaviour to slip past a real-time fraud model? This PoC measures both, and tests which defences actually stop the money from leaving.

    What this shows
    

      
  
    • Text filters are not enough. A pattern-based injection screen cut successful attacks by more than half but let through messages that sound like ordinary supplier emails, and delayed some genuine payments whose wording looked suspicious.
      • 
  
    • Deterministic checks outside the model do the heavy lifting. Policy as code compares the agent's output with the business's own beneficiary records. It never reads the attacker's text, so it cannot be persuaded. Its weak point is the record itself: if a fraudster gets the supplier record changed first, the check passes.
      • 
  
    • Layers cover each other's gaps. Confirmation of Payee catches poisoned records but not inflated amounts; policy catches inflated amounts but not poisoned records. Together they stopped every attack in this run.
      • 
  
    • Fraud models learn shortcuts. The model leaned on "new payee" and "new account" signals. Fraudsters who warm up the payee or use older mule accounts largely disappeared from view. Adversarial training recovered the tactics it was trained on but not the ones it hadn't seen.
      • 

    


    Method and limits
    

    v0.1 is a simulation. The agent follows injected instructions at assumed rates, not rates measured on real models; the human reviewer catch rate and hold delay are also assumptions. All data are synthetic. Zero successes across 1,200 attacks means the true rate is likely below about 0.25%, not that it is zero. The next phase replaces the simulated agent with real LLM agents behind the same interface and repeats every measurement.
